The four-layer preservation methodology

1. Automated extraction

Ingest all COBOL, Pro*COBOL, copybooks, SQL, and Perl wrappers. Resolve every COPY, CALL, and EXEC SQL reference. No black-box treatment.

2. Requirement derivation with citations

Every business rule is tagged with the exact source file + line range. Confidence level assigned: HIGH (directly visible), MEDIUM (inferred from context), LOW (depends on missing artifact).

3. Field-level lineage

Trace every field from input file → working storage → SQL bind variable → Oracle column. Byte offsets verified. Example: the 300-byte TST123-COMMENT-REC is mapped field-by-field across 8 columns.

4. Risk register with SME queue

12 risks identified, each with severity, evidence, mitigation, and explicit "action required of customer SME" items. Nothing is swept under the rug — every gap is documented and trackable.

  3. Classified affected requirements as LOW confidence
  4. Requested the artifacts from the customer

When the customer supplied the full DATECONV subsystem (1,159-line COBOL subprogram + 4 JDN helpers), we:

  1. Ported all 42 date functions faithfully to Python
  2. Built a GnuCOBOL parity harness: 52 test vectors, 51 matched, 1 documented modernization improvement (1900 leap year correction)
  3. The harness caught 13 Python-port defects that all unit tests had missed

02 — The objection

Code quality: no "JOBOL"

"I've heard horror stories of automated tools converting COBOL into Java that still reads and behaves like COBOL, making it impossible for modern Java developers to maintain. What does the output code actually look like?"

The anti-pattern: "JOBOL"

"JOBOL" is Java code that mechanically transliterates COBOL constructs: goto emulated with loops, paragraph names as method names, PIC clauses as raw strings, global mutable state, no type safety. It compiles — but no modern Java developer can maintain it.

What we produce instead: idiomatic Java 21

We don't transliterate. We understand the business intent, then express it using modern Java 21 features. Here's the actual COBOL alongside the planned Java:

private JvControlRecord fetchControlRecord() {
    var result = dispatcher.selectOne(
        """
        SELECT control_record_data
          FROM control_record_table
         WHERE control_record_name = ?
           AND control_record_number = ?
        """,
        CONTROL_RECORD_NAME,
        CONTROL_RECORD_NUMBER
    );

    return switch (result) {
        case Found(var row)
            -> JvControlRecord.fromBlob(
                   row.getString("control_record_data")
               );
        case NotFound _
            -> throw new FetchFailedException(
                   "JV-CONTROL-REC not found"
               );
    };
}

public record JvControlRecord(
    int jvControl1,  // bytes [0:6]
    int jvControl2,  // bytes [6:12]
    int jvControl3,  // bytes [12:18]
    int jvControl4,  // bytes [18:24]
    int jvNumber,    // bytes [24:30] RISK 2
    int jvControl5   // bytes [39:45]
) {
    private static final int BLOB_LEN = 400;

    public static JvControlRecord fromBlob(
            String blob) {
        assert blob.length() == BLOB_LEN;
        return new JvControlRecord(
            Integer.parseInt(blob.substring(0,6)),
            Integer.parseInt(blob.substring(6,12)),
            Integer.parseInt(blob.substring(12,18)),
            Integer.parseInt(blob.substring(18,24)),
            Integer.parseInt(blob.substring(24,30)),
            Integer.parseInt(blob.substring(39,45))
        );
    }
}

public sealed interface DmsResult {
    record Ok()
        implements DmsResult {}
    record NotFound()
        implements DmsResult {}
    record EndOfSet()
        implements DmsResult {}
    record DupKey()
        implements DmsResult {}
    record Fatal(int sqlcode)
        implements DmsResult {}
}

static DmsResult translate(int sqlcode,
        String setName, String fnType) {
    return switch (sqlcode) {
        case  0     -> new Ok();
        case  100   -> !setName.isBlank()
                      && !fnType.equals("FETCH OWNER")
                      ? new EndOfSet()
                      : new NotFound();
        case -1     -> new DupKey();
        case -8103  -> new Ok();
        default     -> new Fatal(sqlcode);
    };
}

"It's not just code; it's data. GERS relies on a massive legacy relational database. How do you handle the data structure transition during the migration?"

Schema parity automation: 16 tests, zero manual checking

An automated test suite compares:

  • DDL table shapes against Oracle DESCRIBE output files
  • INSERT column lists against the DESCRIBE column order
  • 400-byte blob field offsets against copybook PIC clauses
  • 300-byte input slice widths against FD record layout

Known annotated mismatches (tolerated, not ignored):

  • APPROVER width: 14 bytes (FD) vs. 20 bytes (Oracle column) — flagged for SME
  • JC_COUNT_TBL PK: describe file says JC_SUBMITTED (typo); actual PK is JC_SECTION
  • Column name drift: JC_SECTION_COUNT (LABD20) vs. JC_COUNT_NUM (describe file)

Any new drift fails the build. The team cannot accidentally introduce a schema mismatch.

Data transition strategy

Phase 1: Read-compatible

Java reads the same Oracle tables the COBOL writes to. No data migration required during the transition period. Both systems can run in parallel.

Phase 2: Write-compatible

Java writes data in the exact same format as COBOL (same byte layouts, same CHAR widths). The COBOL system can still read Java-written data if needed for rollback.

Phase 3: Schema modernization (optional)

Once COBOL is fully retired, the 400-byte blob can be decomposed into proper relational columns. This is a schema migration, not a code migration — done on the team's timeline.

Risk mitigation: rollback at any point

Because Java writes the same wire format as COBOL, a rollback to COBOL is always possible during Phases 1-2. No "point of no return" until Phase 3.
